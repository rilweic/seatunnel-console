# seatunnel-console 设计文档

> 状态：已确认（2026-10-23）
> 范围：总体设计与分阶段规划。实现细节（表结构、接口定义）在开发阶段另行补充。

## 1. 背景与目标

做一个用来生成和管理 Apache SeaTunnel 任务的平台。提供以下能力：

- **配置任务**：面向新手的场景化向导，同时提供脚本模式
- **调度与启停**：离线任务按时调度、重跑、补数；实时任务启停（P2）
- **查看执行情况**：运行实例的状态、指标、事件、日志，以及数据校验

设计参考 [apache/seatunnel-web](https://github.com/apache/seatunnel-web) 和 [Tapdata](https://docs.tapdata.io/data-replication/create-task)：借鉴领域模型和关键模块的设计，选择性摘抄 seatunnel-web 的代码（Apache 2.0，保留 License 头），**不 fork**。

### 1.1 工程位置与外部依赖

- 本仓库只包含 console；SeaTunnel 和 XXL-JOB 都是外部依赖，安装步骤见 README
- SeaTunnel 按**单独安装的发行包**对待，console 和它之间只通过 REST API 交互，**不依赖 SeaTunnel 的 jar**；查阅 SeaTunnel 行为时看它的源码（`3.0.0-release` 分支），但不修改、不作为编译依赖

### 1.2 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Spring Boot 4.1（JDK 17）。原定 Spring Boot 3，但 3.x 的开源维护已在 2026-06 结束，搭建工程时改为 4.1 |
| 前端 | Vue 3 |
| 元数据库 | MySQL |
| 调度 | XXL-JOB ≥ 3.5.0 |
| 执行引擎 | SeaTunnel Zeta 集群（P1/P2），Flink、Spark（P3） |

**目标 SeaTunnel 版本：3.0.0**（已在 `v3.0.0` tag 上核对过：本文用到的 REST 接口、`restoreMode`/`restoreSourceJobId`、Basic 认证、REST 提交时的 ConfigShade 解密、日志敏感字段打码、`seatunnel-metadata-export.sh` 都存在）。

**JDK 版本**：

| 组件 | JDK | 依据 |
|---|---|---|
| SeaTunnel 3.0.0 集群 | **11** | 编译目标是 Java 8；官方文档写的是 "Java 8 或 Java 11"；CI 只测了 8 和 11。没有测过 17，不要用 17 |
| seatunnel-console | **17** | Spring Boot 4 最低要求 17 |
| xxl-job-admin 3.5.x | **17** | XXL-JOB 从 3.0 起基于 Spring Boot 3 和 JDK 17 |

不能统一用一个 JDK：统一用 17，SeaTunnel 3.0.0 没测过；统一用 11，就用不了 Spring Boot 3 和 XXL-JOB 3.5（拿不到 OpenAPI）。分开用没有问题，因为 console 和 SeaTunnel 跑在各自的 JVM 里，只通过 REST API 通信，也不依赖 SeaTunnel 的 jar。

**约束：不能在 console 进程里内嵌 SeaTunnel 的 jar**，否则要重新评估兼容性。以后升级到主干版本（编译目标 Java 11，支持 11 和 17）时，可以再考虑统一用 17。


## 3. 核心概念

| 概念 | 说明 |
|---|---|
| 用户 | 简单的账号登录，分管理员和普通用户两种角色。不做多租户；按创建人隔离修改权限，详见 §3.1 |
| 项目 | 用来给任务分组，并承载项目参数。**不做权限隔离** |
| 数据源 | 全局共享。连接信息加密存储 |
| 任务定义 | 属于某个项目，类型为批（P1）或流（P2）。有表单模式和脚本模式 |
| 任务版本 | 每次保存生成一个不可变的版本，包含表单 JSON 和 HOCON（只含 `datasource_id`） |
| 调度配置 | 运行时间（页面上按频率选，存为 cron）、重试次数、超时时间、阻塞策略。以 console 为准，同步到 XXL-JOB |
| 运行实例 | 一次实际的运行。记录绑定的版本、计划时间、最终变量值、打码后的配置、Zeta jobId、状态、指标、事件、日志归档、校验结果 |
| connector 元数据 | 参数定义从集群 `/option-rules` 实时读取；中文名称和说明由 console 维护（§7.1） |
| 加密密钥 | 字段加密用的 AES 密钥，管理员维护，加密存储，任务里只引用 ID（§7.11） |

代码从 P1 开始就按"任务类型：批 / 流"做好抽象，避免 P2 时大改。

### 3.1 账号与权限（2026-10-24 实现）

- **可见性**：所有登录用户都能看到全部项目、数据源、任务和运行记录（列表默认只看"我的"，可以切到"全部"）
- **修改权**：项目、数据源、任务只有**创建人或管理员**能修改、删除、运行；运行记录和调度跟着任务走（停止、重跑、补数、改调度都按任务的创建人判断）。数据源的测试连接、浏览库表也算"使用凭据"，同样只限创建人或管理员
- **只能用自己的数据源**：任务引用的数据源（包括行数校验用到的）必须属于任务的创建人，管理员编辑别人的任务时也一样；只能在自己的项目里建任务
- **管理员专属**：用户管理、运行集群诊断、把一个用户名下的项目 + 数据源 + 任务**整体**转给另一个用户（不做单个转移）
- **账号**：管理员建用户并设初始密码，首次登录必须修改（服务端拦截除 `/api/auth/**` 以外的接口，错误码 1005）；管理员重置密码后同样必须修改；用户只禁用不删除；至少保留一个启用的管理员
- **密码与登录**：至少 8 位且含字母和数字；同一账号 10 分钟内连续输错 5 次锁定 10 分钟（内存中，重启解除；管理员重置密码时解锁；记录有上限，随便编的用户名撑不爆内存）
- **改密码后其他会话失效**：自己改密码或被管理员重置后，在这之前登录的其他会话下一次请求就被登出（"密码已修改，请重新登录"）；改密码的这个会话继续有效，并按数据库里当前的角色和状态重建
- 管理员修改用户（角色、启用状态、重置密码）后**立即生效**，不用等对方重新登录：被禁用的用户下一次请求就被登出；角色变化和"必须改密码"在下一次请求时载入会话（变更时间记在内存里，console 单实例部署）
- 旧数据（创建人为空）由迁移 V5 归给第一个管理员

## 4. 执行引擎

### 4.1 选择：Zeta + REST API v2

对比了三种提交方式（源码调研结论）：

| | shell 命令（DolphinScheduler 的做法） | Java 客户端（seatunnel-web 的做法） | **REST API（选定）** |
|---|---|---|---|
| console 机器上要装 SeaTunnel | 要 | 要依赖 SeaTunnel 的 jar | 不需要 |
| 和 SeaTunnel 版本耦合 | 低 | 高（seatunnel-web 因此停在 2.3.11） | 低 |
| 实时任务 savepoint / 指标 | 能做，但要解析命令输出 | 支持 | 支持 |

- DolphinScheduler（`SeatunnelTask`）：执行 `seatunnel.sh --config ... -m cluster`，阻塞等待进程退出码；停止就是 kill 进程。没有 savepoint，也没有指标。
- seatunnel-web（`SeaTunnelEngineProxy`）：内嵌 `SeaTunnelClient`，通过 Hazelcast 连接集群，用线程阻塞在 `waitForJobCompleteV2`。没有定时调度。

用到的接口：`/submit-job`（支持 `restoreMode` 和 `restoreSourceJobId`）、`/stop-job`（`isStopWithSavePoint`）、`/job-info/{jobId}`、`/finished-jobs`、`/logs/{jobId}`、`/overview`。

### 4.2 EngineClient 抽象（长期约束：支持 Flink 和 Spark）

- 第一阶段只实现 `ZetaRestClient`
- **P3 要支持 Flink 和 Spark**。SeaTunnel 的 REST API 是 Zeta 独有的，Flink 和 Spark 要用 `start-seatunnel-flink-*-connector-v2.sh` / `start-seatunnel-spark-*-connector-v2.sh`，或者引擎自己的 API（Flink JobManager REST、YARN、Livy），每种引擎要单独实现
- 连接信息由 console 渲染（第 6 节），和引擎无关，Flink 和 Spark 也能沿用

### 4.3 SeaTunnel 集群的部署前提

写进部署文档，并由"集群健康检查"页面尽可能自动检查：

1. 以 **Zeta 集群**方式常驻运行（混合部署或分离部署）。`-m local` 模式没有 REST 服务
2. `seatunnel.yaml` 中设置 `seatunnel.engine.http.enable-http: true`（代码默认是 false），默认端口 8080
3. 开启 `enable-basic-auth`，建议同时开启 HTTPS
4. **每个节点**的 `connectors/` 和 `lib/` 下放齐所需的 connector 及其依赖，比如 JDBC 驱动。REST 提交时配置在服务端解析
5. `history-job-expire-minutes` 默认 1440，任务结束一天后集群就查不到它了，所以 console 要自己持久化实例数据
6. 实时任务（P2）：checkpoint 放共享存储（HDFS、S3、OSS），建议开启 IMap 持久化
7. console 里配置多个 master 地址，一个连不上就换下一个
8. **每个节点都要开启按作业拆分日志**：在 `config/log4j2.properties` 里把 `rootLogger.appenderRef.file.ref` 改为 `routingAppender`（3.0.0 默认是 `fileAppender`）。否则 `/logs/{jobId}` 返回空列表，console 看不到 SeaTunnel 作业日志（2026-10-24 实测）
9. 用到 Jdbc 连接器时，每个节点的 `lib/` 下都要放对应的 JDBC 驱动
10. SeaTunnel 在**接收任务时**就会校验数据源，比如 Jdbc 的 query 引用了不存在的表。这类失败直接返回 HTTP 500，**响应里没有根因**，也不会生成作业日志；根因只写在 master 节点的 `logs/seatunnel-engine-server.log` 里。console 会把这类失败标记为"提交被拒绝"，并在页面上给出这个提示。（2026-10-24 补充）console 会自己找根因：被拒绝时，用任务引用的数据源把每个 Jdbc source 的查询（query、table_path、table_list 的每一项，带上 where_condition）以 `where 1 = 0` 执行一遍，把数据库的报错写进这次运行的失败原因；脚本编辑器的"检查配置"按钮在保存前做同样的检查

健康检查（"集群健康"页，2026-10-24 实现）分两层：

- **快速检查**（打开页面自动执行，不提交作业）：逐个 master 是否连通、是否开启认证、版本是否为 3.0；worker 节点；所需连接器是否已安装（向导用到的 Jdbc source/sink、Elasticsearch sink，加上所有任务当前版本实际引用的连接器，缺失时列出受影响的任务；通过 `/option-rules` 返回 404 判断，只能检查响应的那个 master）；XXL-JOB admin 是否可访问；console 数据目录是否可写
- **运行诊断**（手动触发）：同时提交几个很小的真实作业。FakeSource → Console 作业结束后能否读到它的日志（检查第 8 条 routingAppender）；每个 MySQL / PostgreSQL 数据源一个 `select 1` 作业（检查第 9 条驱动，以及 worker 到数据库的网络）。最多等 90 秒，超时的作业会被停止

## 5. 调度：XXL-JOB

### 5.1 选型理由

- 调度器只负责"按时调一次 `/submit-job`"，真正执行在 Zeta 上
- XXL-JOB **3.5.0** 开始提供任务增删改、启停和触发的 OpenAPI（AccessToken 改为按执行器隔离）。**低于 3.5.0 的版本不能用**
- 可以直接得到 cron、错过触发后的补偿、重试、超时、阻塞策略、调度日志和高可用
- 没选 DolphinScheduler：它很重，界面不方便；它的 SeaTunnel 插件就是执行一条 shell 命令，管不了实时任务。只有需要复杂 DAG 依赖时才值得引入，目前没有这个需求

### 5.2 集成方式

- console 内嵌 `xxl-job-core` 作为执行器，只注册一个处理器 `seatunnelJobHandler`，参数里带 console 的任务 ID 和计划时间
- **任务配置以 console 为准**：用户在 console 里配置调度，console 通过 OpenAPI 同步到 XXL-JOB。xxl-job-admin 的界面只给管理员看日志、排查问题
- **只有离线任务走 XXL-JOB**。实时任务由 console 直接启停（P2）
- 处理器的执行流程：
  1. 创建运行实例，绑定版本
  2. 渲染变量（第 8 节），在内存中注入连接信息（第 6 节）
  3. 调 `/submit-job`，带上 console 生成的 `jobId`（2026-10-24 补充，见下）
  4. **阻塞轮询** `/job-info`（间隔 2 秒），直到任务结束
  5. 写入最终状态、指标，归档日志，执行行数校验（第 10 节）
  6. 根据结果返回成功或失败，让 XXL-JOB 的超时和阻塞策略生效
- **失败重试由 console 处理器在同一个运行实例内完成，XXL-JOB 的失败重试次数固定为 0**（2026-10-23 改动）。原因是 XXL-JOB 每次重试都会生成一条新的调度日志，处理器无法把它和上一次失败关联起来。每次尝试在 `job_instance_attempt` 里记一条，有各自的 Zeta jobId 和日志，详见 [schema.md](schema.md) §4.2
- **提交不重复**（2026-10-24）：每次尝试由 console 生成引擎 jobId（≥ 2^62，Zeta 自己的 flake id 远小于这个范围），提交时带上。Zeta 遇到同一个 jobId 正在运行时不会再起一份，所以换下一个 master 重发是安全的；提交的响应丢了（超时、断连）时，先按这个 jobId 查一次，引擎已经有这个作业就继续盯着它，查不到才算提交失败
- **提交结果不明时不重试**：引擎客户端区分"肯定没送到"（连接被拒绝，可以按普通失败重试）和"可能送到了但没收到回复"（超时、中断）。后者按 jobId 查 3 次（间隔 5 秒），查到就继续盯着；查不到也确认不了，就记为 FAILED 并写明"请先到集群上确认有没有这个作业"，不重试、不换 jobId。线程被中断时先清掉中断标记再查，查完恢复
- **补数遇到状态不明的运行会暂停**：上一次运行的引擎作业状态不明（可能还在写），补数不会继续下一个时间点，而是暂停并说明原因，确认后点"继续"。补数推进游标和创建这次的运行实例在同一个事务里提交，console 中途停掉既不会跳过时间点，也不会留下「推进了却没有运行」的空档；交给 XXL-JOB 前会再确认补数没被取消。console 重启时，把上次没盯完的运行记为 FAILED、它未结束的尝试记为状态不明，两步在同一个事务里，补数据此暂停
- **有运行中实例的任务不能删除**：删除后就没法从 console 停止它了；有进行中或暂停的补数也要先取消。新建运行实例、新建补数和删除任务都先锁任务这一行，不会在检查和删除之间插进来新的运行或补数。删除任务默认同时删除运行实例、尝试、事件、指标采样、补数批次和归档日志；数据库事务提交成功后才删除日志文件，回滚不会留下找不到日志的运行记录。取消勾选则全部保留，运行记录仍显示原任务名并带“已删除”标记，原任务详情不可再打开
- **提交之后不再有"提交失败"**：查询状态出错（包括 HTTP 500）只记警告、继续轮询；连续 30 次失败（按默认 2 秒的轮询间隔约 1 分钟，再加上每次请求的超时）才停止作业并记为失败。console 失去对作业的掌握（引擎不认识这个作业、停止失败等）时记为 FAILED 并说明原因，**不做失败重试**，以免和可能还在跑的那份重复写入
- 手动运行、重跑和补数时，由 console 先创建运行实例，再把 `instanceId` 放进执行参数，详见 schema.md §4.1
- console 和 XXL-JOB 之间要做对账：发现两边的调度配置不一致时，以 console 为准修正（2026-10-24 实现）。XXL-JOB 的 OpenAPI 没有查询接口，所以对账就是"把 console 的状态再推一遍"：每 10 分钟（启动 2 分钟后第一次）把所有调度重新 update + start/stop，这也会重试之前同步失败的调度；在 admin 里被删掉的任务会重建并恢复调度；没有调度的任务用 stop 探测是否还在，不在就清掉引用，下次运行时重建；console 里已删除、当时没能删掉 XXL 任务的，补删。手动运行、重跑、补数触发时发现任务已被删，也会当场重建再触发。对账只写回同步结果（状态、错误、时间），而且只在调度自读取后没被保存过时才写；期间用户保存过，就读最新的再推一次，不会用旧值覆盖用户刚保存的配置。最近一次对账结果显示在"集群健康"页。判断"任务不存在"依赖 admin 的提示文字（中文、繁体、英文三种都识别）
- **超时和手动终止**：XXL-JOB 因超时或手动终止而中断处理器线程时，处理器会同时停止 Zeta 上对应的任务（不做 savepoint），并记为 CANCELED，避免任务在集群上继续运行却没人知道。调用停止接口前要先清掉线程的中断标记，否则 JDK HttpClient 会立即抛异常，停止请求根本发不出去（2026-10-24 实测修正）
- **在 console 上停止运行**：PENDING 的实例直接用条件更新改为 CANCELED，XXL-JOB 之后再触发时会因为状态不是 PENDING 而放弃。RUNNING 的实例由执行它的线程负责停止：console 给该线程发取消信号，线程立即醒来，先查一次 Zeta 状态（任务若已在两次轮询之间结束，就记录真实结果，不误记为 CANCELED），再调用停止接口，然后每 5 秒查一次，等引擎报告作业结束（最多 30 秒）才记为 CANCELED。停止接口报错，或者 30 秒后作业还没停，就记为 FAILED，并说明作业可能还在集群上运行，不会显示成"已取消"让人以为可以放心重跑（2026-10-24 补充）。取消信号只在本进程内存里，所以要求 console 单实例部署
- **调度配置的同步**：保存调度时先写 `job_schedule`（sync_status=PENDING），再把任务对应的那一个 XXL-JOB 任务改为 CRON，启用时 start、停用时 stop。同步失败时记为 FAILED 并保存错误信息，用户修正后重新保存即可。cron 用 Quartz 语法（6 段，日和周必须有一个是 `?`，不支持年字段），console 在本地先校验并预览接下来 5 次触发时间。页面上不直接让用户写 cron：按"每隔几分钟 / 每小时 / 每天 / 每周 / 每月"选频率和时间，自动生成 cron 并用中文复述（`components/CronEditor.vue`）；读不回这些选项的 cron 以"自定义"方式手写。离线任务两次运行至少间隔 2 分钟：保存和预览时取未来一年内的触发时间检查，太密（如每秒、每分钟，或只在某个小时内每分钟）直接报错，避免误配成高频调度
- **调度的超时和阻塞策略对手动运行同样生效**，因为手动运行触发的是同一个 XXL-JOB 任务。失败重试只对定时运行生效
- **XXL-JOB 会提前 5 秒预读触发**（`PRE_READ_MS`）：在下一次触发前 5 秒内停用调度，这一次仍可能会触发
- **计划时间**：定时触发时用 XXL-JOB 触发日志的时间；手动运行、重跑和补数时，由 console 在执行参数里明确传入 `scheduledTime`
- 执行参数格式：`{"jobDefinitionId": 12, "scheduledTime": "2026-10-22T02:00:00", "params": {...}}`
- 执行器设置 `glueEnabled=false`，不执行从 admin 界面下发的脚本，只运行 BEAN 处理器

## 6. 数据源与凭据安全

**原则：保存下来的任何配置里都不出现密码。**

1. 任务定义和各个版本里**只保存 `datasource_id`**
2. **只在提交那一刻**，在内存中把连接信息渲染进 HOCON，然后直接发给 `/submit-job`
3. 运行实例上归档的"实际执行配置"保存的是**打码后的版本**
4. 不管是 XXL-JOB 处理器还是 console，日志里都不能打印渲染后的配置
5. 和集群通信必须开启 HTTPS 和 Basic 认证
6. 防止用户自己把密码写进可见的地方（2026-10-24 补充）：
   - 整份配置（env、source、transform、sink，嵌套对象和数组都查）里选项名像凭据的（含 password、passwd、secret、token、credential、api_key、access_key），或者值里带密码的（URL / 连接串里参数名像凭据的，按解码后的名字判断，如 `clientCertificateKeyStorePassword=`、`%70assword=`；以及 `scheme://user:密码@host`），保存版本时直接拒绝，提示改用数据源；向导的高级选项同样适用
   - 打码版本（预览、运行归档）把这类选项和 URL 里的密码一律替换成 `******`，包括配置里直接写的
   - 选项名像凭据时，不管值是普通值、数组还是对象，只要有内容就算
- 数据源归属不只在保存时检查，每次渲染（运行、预览、检查）都按渲染后的配置再查一次：防止保存时写 `datasource_id = "${ds}"`，运行时用启动参数把它换成别人的数据源
   - 数据源的"连接参数"（拼在 JDBC URL 后面、明文保存）里写 password / sslpassword 之类，保存和测试连接时拒绝
   - "测试校验"会用数据源的凭据执行计数，所以和保存版本一样，只能用任务创建人自己的数据源
7. 字段加密的密钥同样不进配置（2026-10-25）：配置里只写 `encrypt_key_id`，提交时在内存里换成密钥，打码版本里是 `******`；脚本的 FieldEncrypt 块里直接写 `key` 视同明文密码拒绝保存（§7.11）

依据：`/job-info` 返回的 `jobDag` 只包含 `envOptions`、vertex 名称和表路径，不包含 connector 参数；SeaTunnel 打日志时会按 `ConfigShadeUtils.DEFAULT_SENSITIVE_KEYWORDS`（password、username、auth、token、access_key、secret_key）自动打码。

**可选加固（暂不做）**：REST 提交支持 `ConfigShade`（`RestUtil` 会调用 `ConfigShadeUtils`）。console 先用 AES 加密密码，在配置里写上 `shade.identifier = "aes"`，Zeta 节点上放一个解密 jar 即可。

**没采用的方案**：用 Metadata SPI（`MetadataProvider` + `metadata_datasource_id`）做一个插件，让集群节点直接读 console 的数据库。否决原因：链路长，每个节点都要放数据库账号和密钥，而且元数据 SPI 只支持 Zeta，和 Flink/Spark 的长期约束冲突。

### 6.1 数据源类型

| 阶段 | 类型 |
|---|---|
| P1 | MySQL、PostgreSQL、Elasticsearch |
| P1 之后（2026-10-25 提前到 P2 前） | HTTP 接口（只作来源，§7.13） |
| P3 | 按需扩展 |

每种数据源类型是 console-datasource 里的一个插件（`DataSourcePlugin`），要实现：校验和测试连接、列出库/表/索引、读取表结构、"数据源 → 对应 connector 配置项"的翻译（例如 Jdbc 用 `url/driver/user/password`，CDC 用 `base-url/username/password`）、列表里显示的地址，以及**能力声明**（`DataSourceCapabilities`，2026-10-26）：

| 能力 | 含义 | MySQL / PG | ES | HTTP |
|---|---|---|---|---|
| 向导来源 / 目标 connector | 向导生成哪个 SeaTunnel source / sink，空表示向导不能用它做来源或目标（脚本仍可） | Jdbc / Jdbc | - / Elasticsearch | Http / - |
| 有库 / schema 层 | 先选库或 schema 再选表 | 是 | 否 | 否 |
| 多表 | 一个向导任务可以选多张表 | 是 | - | 否（一个任务一个接口） |
| 计数方式 | 行数校验怎么数：SQL 计数 / 按索引计数 / 不能计数 | SQL | 索引 | 不能 |
| 最大并行度 | 向导任务读它时最多用多少并行 | 8 | - | 1 |
| 名字小写 | 目标名必须小写 | 否 | 是 | - |
| JDBC 驱动 | 集群诊断要检查 worker 上的驱动 | 是 | 否 | 否 |

JDBC 数据库另外声明 SQL 方言（`SqlDialect`：标识符怎么加引号、库/schema 在 `table_path` 里怎么写）。前端通过 `GET /api/datasources/types` 读取类型列表和能力，页面上不再写死类型名。

## 7. 任务配置

### 7.1 connector 元数据

- 指的是连接器配置参数的**定义**（不是用户填的值）：参数名、类型、默认值、是否必填、官方说明
- 来源（2026-10-24 改）：console 直接调用集群的 `GET /option-rules?type=source|sink&plugin=<名称>`，按插件缓存在内存里。不再导出 JSON 上传，`seatunnel_metadata` 表不再使用
- **用途只限于**渲染向导里默认折叠的"高级参数"，以及填写时的类型提示。**不直接拿它当用户界面**
- 高级参数的中文名、说明、分组和输入控件由 console 自己维护（`console-ui/src/utils/connectorOptions.ts`）：常用参数按"读取性能 / 并行切分 / 写入"等分组显示中文；很少需要改的参数折叠在"更多参数"里；向导已处理、属于数据源、或对 MySQL/PG/ES 不适用的参数（账号密码、XA 事务、Oracle 模式、字段名大小写、已废弃参数等）不显示，除非以前已经设过值。集群新增、字典里没有的参数也放在"更多参数"，显示 SeaTunnel 原文说明

### 7.2 场景化向导（面向新手）

用户回答的是业务问题，不需要认识 SeaTunnel 的参数名。每个选项的中文文案、默认值，以及它们和 SeaTunnel 参数的对应关系，都由我们自己维护。**HOCON 由服务端根据表单生成**，前端只负责收集表单。

支持的组合（P1）：源端 MySQL、PostgreSQL；目标端 MySQL、PostgreSQL、Elasticsearch。ES 作为源端只能用脚本模式。

| 步骤 | 内容 |
|---|---|
| ① 来源 | 选数据源 → 选一个库（MySQL）或 schema（PG）→ 勾选一张或多张表（console 实时查询，标出有无主键）。**正则只用来筛选列表**，保存的是勾选出来的明确表清单，不会自动纳入以后新建的表 |
| ② 目标 | 选目标数据源 → 库或 schema（必须已存在，不自动建库）。下方"表映射"逐行列出 源表 → 目标表，可以按规则批量改名，也可以直接改某一行（7.8）。目标端选项见 7.4 |
| ③ 字段与同步方式 | 选全量或增量（7.5）。下方"字段映射"左边是表，右边是选中表的字段：屏蔽（不同步）或恢复字段、改目标字段名（规则或手改，7.8），以及这张表的固定过滤条件、单独的增量字段。**不推算目标类型**：只显示源字段和类型；目标表已存在时按映射后的字段名对比。建表交给 SeaTunnel 的 `schema_save_mode` |
| ④ 并行度与校验 | 并行度 1/2/4/8，默认 1（单表按主键自动切分；多表时多张表同时读）。失败重试、超时在"调度"页配置，这里不重复。行数校验默认开启并自动生成（7.6）。连接器的高级参数折叠在这里 |
| ⑤ 预检查与预览 | 自动执行预检查（错误不能保存，警告可以保存），只读展示生成的 HOCON，确认后保存为新版本 |

**生成规则**：每张表生成 `table_path`；有字段裁剪、过滤条件或增量条件时，再生成该表自己的 `query`（不用全局 `where_condition`，因为它对所有表生效）。改名通过 transform 实现（7.8）。sink 端用 SeaTunnel 的占位符 `${table_name}`、`${primary_key}`，console 的变量检查会忽略这些占位符，它们也不能用作参数名。

**预检查**：连通性；源库、表、字段、增量字段是否存在，增量字段是否为时间类型；没有主键的表；目标库是否存在；目标表名、字段名是否为空、含非法字符或重名（7.8）；目标表或索引是否已存在、映射后的字段是否都在；"增量 + 清空后写入"这类互相冲突的组合。

### 7.3 链路形态与脚本模式

- P1 只支持线性链路：一个 Source、零到多个 Transform、一个 Sink。多表同步通过 Source 自身的多表配置项实现
- 向导里的表 / 字段映射（§7.8）和字段处理（§7.10、§7.11）都生成为 Source 和 Sink 之间的 transform，按源表分别配置；脚本模式可以从模板插入 transform（§7.12）
- 新建任务时选"向导"或"脚本"。向导任务每次保存同时存表单（`job_version.form_json`）和生成的 HOCON，重新编辑时回到向导并带上上次的选择
- **脚本模式**：可以直接编辑 HOCON，照样能引用 `datasource_id` 和变量。**只能从向导转到脚本，不能再转回向导**，转换前二次确认

### 7.4 目标端选项（每个任务单独配置，对所有表生效）

| 选项 | 可选值 | 默认值 |
|---|---|---|
| 目标表或索引不存在时 | 自动创建（`schema_save_mode = CREATE_SCHEMA_WHEN_NOT_EXIST`）/ 报错（`ERROR_WHEN_SCHEMA_NOT_EXIST`） | 自动创建 |
| 写入模式 | 按主键 upsert / 追加 | 所选表都有主键时用 upsert，否则追加 |
| 已有数据 | 保留（`APPEND_DATA`）/ 清空后写入（`DROP_DATA`，**醒目提示**） | 有主键时保留；没有主键且是全量同步时，默认清空后写入，避免每次运行都重复写入一遍 |

- 增量同步时不允许"清空后写入"
- ES 目标：索引名必须小写；upsert 时用 `primary_keys = ["${primary_key}"]` 按各表主键生成 `_id`，追加时由 ES 自动生成 `_id`；索引不存在时自动创建，字段映射由 SeaTunnel 推断

### 7.5 离线增量

增量字段只能是时间类型（date、datetime、timestamp）。时间窗口可选"连续增量"（默认）、"按天"、"按小时"，或者"自定义条件"（自己写 where，可以用变量，用于数字型自增 ID 等其他情况）。

**连续增量**（2026-10-26 实现并实测）：每次从上次成功同步到的位置接着同步，生成

```sql
updated_at >= '${system.window.start}' and updated_at < '${system.window.end}'
```

- **窗口** = `[水位, 计划时间 − 延迟)`。水位 `job_definition.watermark` 是上一个成功窗口的终点，null 表示从最早的数据开始（`1970-01-01 00:00:00`）；延迟 `window_lag_seconds` 默认 60 秒，给还没提交的事务留时间。时间截到秒
- **哪些运行有窗口**：配置（模板、项目参数、任务参数、启动参数）里引用了 `${system.window.start}` 或 `${system.window.end}` 的运行。向导和脚本一样，脚本里写这两个变量也是连续增量
- **窗口在运行开始时确定**，写进 `job_instance.window_start / window_end`。之后的重试、行数校验、运行详情都只读这两列
- **推进水位只有一条规则**：运行成功（包括行数校验通过）后执行 `UPDATE job_definition SET watermark = 窗口终点 WHERE watermark <=> 窗口起点 AND watermark_gen = 运行开始时读到的值`。`watermark_gen` 每次手动调整水位加 1，所以重置成和窗口起点相同的值也拦得住（2026-10-27 补）。窗口接不上当前水位（期间有别的运行推进了水位，或水位被重置）就不推进，时间线里记一条 WINDOW 事件说明原因。这一条规则覆盖了所有情况：
  - 失败：不推进，下一次运行的窗口从原水位开始，把失败的那段一起同步
  - 重跑：沿用原实例的窗口，同步的是原来那段数据。失败后还没有别的运行成功时，重跑成功会推进水位；之后的运行已经同步过这段时，重跑只把这段再写一遍
  - 补数：每次运行的窗口是 `[上一个触发时间 − 延迟, 本次触发时间 − 延迟)`（没有调度时按天），整批首尾相接，和当前水位无关；正好接上水位时才推进
  - 重置水位：任务详情「增量水位 → 调整」，可以设成某个时间或清空（从最早开始）。正在运行的不受影响，结束后也不会覆盖新水位
  - 并发：两次运行读到同一个水位时，只有先成功的那次推进水位，另一次只是重复写了同一段
- **窗口为空**（水位已经不早于窗口终点，比如计划时间早于水位的手动运行）：不提交作业，直接记为成功，不推进水位
- **写入方式**：失败前已经写入的部分会在下次再写一遍（至少一次），所以要按主键更新写入；向导里选了追加写入时，预检查给出警告
- 一个任务一个水位，多张表共用。后来加进任务的表只会从当前水位开始同步，需要的话先补数或调整水位
- 没有做单次窗口的长度上限：停了很久之后的第一次运行窗口会很大，按主键更新写入时只是一批数据量大一些

**按天 / 按小时**：窗口只由计划时间决定，和其他运行无关，适合每天或每小时运行一次、按天整段处理的任务（比如从 DolphinScheduler 迁过来的）。调度比窗口更频繁时，每次都会重复同步同一段，调度页会给出警告。按天生成：

```sql
updated_at >= '$[yyyy-MM-dd-1] 00:00:00' and updated_at < '$[yyyy-MM-dd] 00:00:00'
```

按小时生成 `>= '$[yyyy-MM-dd HH-1/24]:00:00' and < '$[yyyy-MM-dd HH]:00:00'`。多表时可以给所有表设一个同名增量字段，单张表也可以单独指定。补数和重跑会按各自的计划时间算出正确的时间窗口。

**自定义条件**：编辑框旁边可以「插入变量」（同步窗口、时间表达式、内置变量、任务参数），下方按下次运行实时显示渲染后的条件（`POST /api/jobs/{id}/render-text`）。查询里留下没有定义的 `${name}` 时预检查报错、不能保存：在 SQL 里它不可能是 HOCON 替换，只能是拼错或者没定义的参数。

### 7.6 向导任务的行数校验

向导知道源表、目标表、过滤条件和增量窗口，所以会自动生成**按表**的计数校验：

- 全量 + 清空后写入：源端按过滤条件计数，目标端统计整张表
- 增量：两端都按同一个增量字段和同一个时间窗口计数（增量字段被裁掉时，这张表不做校验）
- 全量 + 保留已有数据：目标表里可能还有源端已删除的数据，计数不准，**默认关闭并说明原因**
- ES 目标：只在"全量 + 清空后写入"时校验（`_count`），增量窗口的日期格式在 ES 里不好保证一致，P1 不做

### 7.7 版本管理

- 每次保存都生成一个不可变的新版本
- 支持查看版本差异和回滚（2026-10-24 实现）：版本页选任意两个版本对比配置和任务参数的行级差异；回滚是把旧版本的内容另存为一个新版本并设为当前版本，历史只增不改。向导任务回滚时用旧版本的表单重新生成配置并重新预检查
- 运行实例绑定它所用的版本；实时任务（P2）编辑后提示"新版本待重启生效"

### 7.8 表与字段映射（2026-10-24，参考 Tapdata）

- **表名**：规则 = 查找替换（普通文本，替换全部出现处）→ 大小写（不变 / 大写 / 小写）→ 前缀 + 后缀，存在 `target.tableRule`；某一行手改的名字存在该表的 `targetName`，优先于规则，"重置"会一并清掉。ES 索引名一律转小写。旧表单（`prefix` / `suffix` / 单表 `tableName`）打开时自动换算成规则和手改名，映射结果不变
- **字段**：屏蔽 = 不同步（仍存在 `columns`，`null` 表示全部）；字段名规则（大小写、前缀、后缀）可以作用于当前表（`TableSpec.fieldRule`）或全部表（`fieldRule`）；手改的名字存在 `fieldNames`。不支持改类型、调整顺序、计算字段
- **最终名字由 console 算好再写进配置**（前端 `utils/naming.ts` 预览、服务端 `WizardGenerator.targetName / targetField` 生成，两边规则一致），页面上看到的就是实际写入的。规则作用于保存时的字段清单，之后源表新增的字段沿用原名
- **生成方式**：字段改名用 `FieldRename`（`table_transform` 按源表 `table_path` 配 `specific`），表改名用 `TableRename`（按源表配 `replace_from = "^.*$"`），只为有变化的表生成；sink 一律写 `${table_name}`。**不用 SQL 别名改字段名**：Jdbc source 带 `query` 时按字段名把查询结果和表元数据合并，主键字段改名后主键信息会丢，upsert 和自动建表都会出错；`FieldRename` 会连同主键约束一起改名（已实测：改名后的 `ID` 仍是目标表主键）
- **校验**：目标名为空、含空格 / 点 / 引号 / `$` / 反斜杠、两张表映射到同一目标表、同一表两个字段映射到同一名字（均不区分大小写）都是错误；upsert 时主键字段不能屏蔽；目标表已存在时缺少映射后的字段是错误，多出的字段只提示
- 行数校验按映射后的目标表名计数；增量窗口在目标端用映射后的增量字段名

### 7.9 任务复制（2026-10-25）

- 入口：任务列表每行的"复制"、任务详情"更多 → 复制任务"。填新名称（默认"原名_copy"）和项目（只能选自己有编辑权的项目）
- 复制当前版本的配置（向导表单或脚本）、任务参数、行数校验和描述，作为新任务的 v1（备注"复制自 原名 vN"）；**不重新跑预检查**，数据源暂时连不上也能复制
- 调度设置一起复制但**不启用**（复制后再走一次 XXL-JOB 同步；同步失败不影响复制，只是没有调度）
- 不复制运行记录、补数、历史版本
- 新任务的创建人是复制的人，所以只能用复制人自己的数据源；原任务用到别人的数据源时拒绝复制并说明是哪个数据源（管理员也一样）

### 7.10 字段处理（2026-10-25，用 SeaTunnel transform 实现）

向导第 3 步的字段映射里按表配置，全部做成选项，不让用户写 SQL（"高级：手写表达式"除外）：

- **处理已有字段**（每个字段的"处理"）：值替换（普通文本或正则，正则替换里可以用 `$1`）→ 脱敏（手机号保留前 3 后 4、身份证前 6 后 4、邮箱只留首字母和 @ 后、姓名只留姓、银行卡只留后 4、自定义前 N 后 M 和替代字符；长度不够原样保留，结果是文本）→ 类型转换（字符串、整数、小数(p,s)、日期、日期时间、布尔；**失败置空**，用 `TRY_CAST`）→ 加密（7.11）。主键字段不能处理
- **新增字段**：常量或变量（固定值 / 内置变量 / 日期时间，和参数编辑器一样选；日期、日期时间类型按值的格式用 `PARSEDATETIME` 解析）、拼接、截取、大小写/去空格、日期格式化、数值计算、为空时默认值、UUID、当前时间、高级手写表达式（SeaTunnel SQL，预检查只给警告）。结果类型可选
- **提取字段**：JSON 路径（多个路径各成一个字段）、正则（每个分组一个字段，个数要一致）、按分隔符拆分（段数不够为空，多出来的放进最后一个字段）；取不到的为空；可选"提取后不同步来源字段"（主键不行）
- 新字段直接用填的名字，不受字段名规则影响，写在目标表最后；参与重名检查和"目标表已存在时缺少字段"检查（已存在的目标表不会自动加字段）
- **生成方式**（2026-10-25 在 3.0 集群上实测）：每张表按固定顺序 JsonPath → RegexExtract → Split → 一个 `Sql`（`select 每个字段及其处理表达式, 新字段 from dual`）→ FieldRename → TableRename；都通过 `table_transform` 按源表 `table_path` 配置，同一张表多个提取用 `rule_match_mode = ALL_MATCH`；顶层用 `table_match_regex = "(?!)"` 不匹配任何表，只为满足插件的必填项，没配置的表原样通过。JsonPath 设 `column_error_handle_way = SKIP` 让取不到的值为空
- **Sql 里的字段引用不加引号**：Sql 对"直接引用的列"会沿用源列的类型和长度，加了反引号就丢长度（CHAR(36) 主键会变成 longtext，MySQL 自动建表失败）。只有不是普通标识符或是保留字的列名才加反引号；双引号 Sql 不认
- 预检查：引用的字段存在且同步、主键不被处理或去掉、正则可编译且分组数等于新字段数、JSON 路径以 `$` 开头、小数位数合法、新字段名合法不重名；手写表达式给警告

### 7.11 字段加密与加密密钥（2026-10-25）

- 字段处理里的"加密"用 SeaTunnel `FieldEncrypt`（默认 AES-GCM），在替换、脱敏、类型转换之后、改名之前执行；加密字段先在 Sql 里转成文本，因为密文比原字段的声明长度长。主键不能加密
- **密钥不能出现在配置里**（和数据源密码一样，§6）：管理员在"运维管理 → 加密密钥"里新建（自动生成 128/192/256 位，或导入自己保管的 Base64 密钥），用 `CONSOLE_SECRET_KEY` 加密后存 `encrypt_key` 表；**创建后不能再查看**，只能停用不能删除。要在别的系统解密，就用导入的方式
- 任务按表选择密钥，配置里只写 `encrypt_key_id`；提交运行时 `JobConfigRenderer` 在内存里换成 `key`，存档的配置里是 `******`；保存版本时检查引用的密钥存在且启用，停用的密钥会让运行失败
- 脚本模式里直接写 `FieldEncrypt { key = "..." }` 会被当成明文密钥拒绝保存（`key` 这个名字只在 FieldEncrypt 块里当密钥看待）
- 2026-10-25 在 3.0 集群上实测：生成的配置加密后，用同一个密钥 `mode = decrypt` 解密，和源表逐行一致（含空值）

### 7.12 脚本模式插入 transform（2026-10-25）

- 脚本编辑器上方"插入 transform"：常用插件（Sql、FieldRename、TableRename、Filter、Replace、Copy、JsonPath、RegexExtract、Split、FieldEncrypt、TableFilter）各有一个带中文注释的模板，可以先改再插入；下方列出该插件的全部参数，说明是集群 `/option-rules?type=transform` 的原文
- 脚本里还没有 `transform {}` 时，在 `sink` 前面新建一个；已有时插到光标处
- FieldEncrypt 模板用 `encrypt_key_id`，不写 `key`（7.11）

### 7.13 HTTP 接口来源（2026-10-25 实现）

用 SeaTunnel 的 `Http` source（`connector-http-base`）把接口返回的 JSON 同步到 MySQL、PG、ES。它的限制决定了下面的设计：一个 source 对应一个接口、不能并行、没法计数；JSON 必须写 `schema.fields`；认证只能写在 `headers` 里；分页有页码和游标两种。

**范围**：新增「HTTP」数据源类型；向导支持 HTTP → MySQL/PG/ES，只做离线、`format = json`。实时轮询、`text` / `binary` 格式、OAuth2（要先换 token）不做，需要时用脚本模式（同样可以引用 `datasource_id`）。

**数据源和任务的分工**：

| 存在哪 | 内容 |
|---|---|
| 数据源（一个系统一个） | 基础地址（如 `https://api.example.com/v1`，不能带 `?` 参数和 `#`：任务路径接在它后面，带了参数路径就会被吞进参数里；公共参数写到任务的请求参数里）、认证、公共 Header、连接和读取超时、可选的测试路径 |
| 任务（一个接口一个） | 路径、GET / POST、请求参数、POST Body、分页、数据位置、字段、主键 |

- 认证方式：无、Bearer Token、Basic（用户名 / 密码）、API Key（自定义 Header 名或 query 参数名）。凭据和数据库密码一样加密保存、不回传浏览器，提交时由 `toConnectorOptions` 渲染进 `headers` / `params`，归档配置里是 `******`（§6）。baseUrl 不允许 userinfo 或敏感名称的 query 参数，避免绕过加密存储
- 测试连接：带认证 GET「基础地址 + 测试路径」（不填测试路径就请求基础地址）。2xx 成功；401 / 403 提示认证失败；其他显示状态码和响应开头 200 个字符
- 向导用到的 HTTP 请求（测试连接、请求预览）都由 console 服务端发出，所以 console 和 SeaTunnel 节点都要能访问这个接口；响应会替换原始凭据及完整 Bearer / Basic 认证值，避免接口回显请求头时泄露。query API Key 与任务参数同名时，预览和运行都直接报错，任务参数不能覆盖认证

**向导各步**：

| 步骤 | HTTP 来源时的内容 |
|---|---|
| ① 来源 | 选 HTTP 数据源，填请求：路径、方法、参数（键值表格，值可以用变量）、POST 时的 JSON Body；再选分页（见下）。一个任务一个接口，要同步多个接口就建多个任务（可用任务复制）。路径和参数一样支持变量；引用数据源时禁止绝对 URL，避免把数据源认证发送到其他主机，预览和运行都只有「基础地址 + 相对路径」 |
| ① 请求预览 | 「发送请求预览」用当前配置真实请求第一页，显示返回的 JSON。用户在 JSON 树上点选数据所在的数组，保存为 `content_field`；console 用前几条记录推断字段和类型（可以改）→ `schema.fields`；嵌套字段可以勾选展开。所有字段保存明确的 `jsonPath`，来源字段名只读，改名统一在第③步做。DECIMAL 可填总位数和小数位（默认 18,2），生成带精度的 schema；服务端只接受页面提供的类型白名单。SeaTunnel 的 TIMESTAMP 不能读取带 `Z` 或偏移量的时间，这类字符串默认推断为 STRING；不带时区的本地时间仍推断为 TIMESTAMP。预览的响应不保存。SeaTunnel 同时设置 `content_field` 和 `json_field` 时会忽略后者，所以生成配置统一用 `json_field = 数据数组路径[*].字段路径` 提取记录，不再单独生成 `content_field` |
| ② 目标 | 同数据库来源，只有一行"表映射"：目标表名必填，默认取路径最后一段。生成时写成 `schema.table`，所以 sink 的 `${table_name}`、`table_transform` 都按这个名字走，不再需要 TableRename |
| ③ 字段与同步方式 | 字段映射和字段处理照常可用（§7.8、§7.10、§7.11）。回第①步改类型、主键或路径时保留已屏蔽字段，只去掉不存在的字段并追加真正新增的字段；HTTP 任务只有一张表，路径最后一段（表名）变了也保留这张表的屏蔽、改名和字段处理。主键可选：选了就生成 `schema.primaryKey`，写入默认 upsert；这时 schema 改用 `columns` 写法，主键列 `nullable = false`、字符串主键 `columnLength = 255`（`fields` 写法一律可为空，MySQL / PG 自动建表会因主键可为空而失败，字符串还会建成 LONGTEXT，不能做主键；2026-10-25 在集群上实测）；不选就强制追加（即使表单残留 UPSERT；高级参数也不能设置 `enable_upsert`、`primary_keys` 等向导生成的参数，所有来源都一样），全量时默认清空后写入（沿用 §7.4）。没有"增量字段"，增量见下 |
| ④ 并行度与校验 | 并行度固定为 1；行数校验关闭（接口无法计数），说明原因，运行页照常显示引擎读写条数。高级参数只允许重试次数、两项重试退避和 `json_filed_missed_return_null`，其他参数由服务端拒绝，不能覆盖 format/schema/pageing 等生成配置。超时在数据源配置；当前 SeaTunnel Http source 没有 `request_interval_ms`，不生成也不接受这个参数 |
| ⑤ 预检查与预览 | 数据源连通；按配置请求第一页，检查 `content_field` 能取到数组、字段都在；目标端检查同数据库来源。JSON 路径支持点字段、引号包裹的字段名和数组下标，非法路径直接报错，不静默跳过。第一页为空时仍校验所有字段路径；顶层字段可用简单字段名（字母、数字、下划线和 `-`，按 SeaTunnel 用的 JsonPath 2.7.0 实测能取到值）代替 jsonPath，显式填写则必须以 `$` 开头，含其他字符的字段名必须显式填写。分页参数和 Body 的拼装由预览和生成配置共用一份代码，预览只是把 `${page}` 换成起始页 |

**分页**（统一生成 `pageing.use_placeholder_replacement = true`）：

- 不分页
- 页码：页码参数名、放在参数还是 Body、起始页、每页条数的参数名和值；结束条件选"返回条数小于每页条数"（`batch_size`）或"固定总页数"（`total_page_size`）。query 参数同时生成 `keep_page_param_as_http_param = true`，每轮直接注入当前页码，避免 `${page}` 第一次替换后一直重复首页；Body 用 `${page}`，连接器会保留原始 Body 再逐页替换
- 游标：游标参数名、响应里的游标路径（`cursor_response_field`）。首期只支持 query 参数，生成 `keep_page_param_as_http_param = true`，第一次请求不写入游标参数，后续由连接器根据响应自动加入；当前连接器无法可靠处理 Body 里的首次空游标，因此不支持 Body 游标。游标路径保存时校验语法（不带 `$` 的名字按根字段处理，和 Jayway 一致），预检查在第一页取不到游标时给警告
- `page`、`cursor` 是保留名，不能用作任务参数名，console 的变量替换也不碰它们（同 `${table_name}`）

**增量**：接口没有增量字段，增量靠请求参数带时间窗口。参数值支持变量，旁边有「按天 / 按小时」快捷插入（如 `start=$[yyyy-MM-dd-1]`、`end=$[yyyy-MM-dd]`），补数和重跑按计划时间算出各自的窗口（§7.5、§8）。

**凭据检查扩展**（§6 第 6 条）：HTTP 下凭据常写在 Header 里，所以 Header 名 `Authorization`、`Cookie`、`X-API-Key`，以及名字含 key / token 的 Header，也算作凭据：任务配置（含脚本、高级参数）里直接写会拒绝保存，打码时一并替换。数据源公共 Header 与脚本共用同一套规则，password / secret / credential 等敏感名称也不能明文保存。JSON 格式的 Body 里键名像凭据且有值（如 `{"token":"..."}`）同样拒绝保存。任务的 Header 和参数不能和数据源的同名（Header 不分大小写）：API Key 可以叫 `appId` 这类看不出是凭据的名字，同名就会把认证换掉。认证只能放在数据源的专用字段里。

**实现与验证**：数据源类型和测试连接 → 请求预览和字段推断 → 向导生成和预检查 → 凭据检查扩展。预览只发一次请求、最多读取 2 MB、默认不跟随重定向；单元测试和本地 mock HTTP 服务覆盖认证、GET/POST、字段推断和分页。真实 SeaTunnel 集群已验证 query 页码与 query 游标：均读取两页（第二页为空）并准确写入 2 条，嵌套 JSON 字段正常。集群健康检查的 Http 连接器只在现有任务实际使用时列为必需，不因为支持 HTTP 来源就要求所有集群安装。

### 7.14 模块划分：数据源和向导按插件扩展（2026-10-26）

目标是加一种数据源时只新增文件、不在已有代码里加分支（新增步骤见 CLAUDE.md「Adding a datasource type」）。分三层：

1. **数据源插件**（console-datasource，按数据源类型）：连接、元数据、connector 配置项、地址和能力（§6.1）。加一种 JDBC 数据库只需要一个继承 `JdbcDataSourcePlugin` 的插件，复用或新增一个 `SqlDialect`
2. **向导的来源和目标**（console-server `job/wizard/source`、`job/wizard/sink`，按 SeaTunnel connector）：`WizardSource`（`JdbcSource`、`HttpSource`）负责自己那部分表单、source 配置块和对实时数据源的预检查；`WizardSink`（`JdbcSink`、`ElasticsearchSink`）负责 sink 自己的配置项和行数校验的目标端。`WizardConnectors` 按插件声明的 connector 选出它们，JDBC 的方言由插件给出。`WizardGenerator` 只负责编排（source → 共用的 transform → sink）和所有任务共用的检查，`WizardService` 只做共用的预检查（字段是否存在、主键与写入方式、字段处理、目标表），都不再判断类型
3. **前端**：数据源页按类型注册表单组件（`components/datasource/forms.ts`，JDBC 数据库共用 `JdbcFields`）；向导按 connector 注册（`components/wizard/connectors.ts`）：每种来源提供第①步组件（`JdbcSourceStep` 选库选表、`HttpSourceStep` 配请求和预览）、说明文字、取字段和检查第①步的方法；其余地方读能力（并行度上限、能否计数、有无库层、名字小写）

表单里各来源自己的设置放在 `source.spec`，由对应的来源解析（HTTP 是 `HttpSpec`）。以前保存为 `source.http` 的版本照常读取，再保存时写成 `spec`。

验证方式：`wizard-golden/` 下用旧格式保存的 8 份表单（MySQL、PG、ES、HTTP，含改名、字段处理和各种行数校验分支）生成的配置、校验和说明必须与基准文件逐字一致，重构前后没有变化；`WizardGoldenTest` 会自动对比。

## 8. 变量

照搬 DolphinScheduler 的写法，方便以后迁移。

- **内置变量**：`${system.biz.date}`（计划时间的前一天，yyyyMMdd）、`${system.biz.curdate}`、`${system.datetime}`，以及实例 ID、任务名等
- **时间表达式**：`$[yyyyMMdd-1]`、`$[HHmmss-1/24]`、`$[add_months(yyyyMMdd,-1)]`、`$[this_day(...)]`、`$[last_day(...)]`、`$[month_first_day(...,N)]`、`$[month_last_day(...,N)]`、`$[week_first_day(...,N)]`、`$[week_last_day(...,N)]`、`$[year_week(...)]`
- **优先级**（从高到低）：启动参数（手动运行或补数时填写）> 任务参数 > 项目参数 > 内置参数。没有"上游传参"，因为没有 DAG
- **时间基准**：XXL-JOB 的**计划触发时间**，不是实际运行时间，保证重跑结果一致
- **和 HOCON 的冲突**：HOCON 自己也用 `${}`。console **只替换它认识的变量名**，不认识的原样保留；`$[...]` 不存在冲突
- 实例上记录最终变量值和渲染后（打码）的配置

实现细节（2026-10-24 实现并实测）：

- **替换是文本级的**，在解析 HOCON 之前进行，所以 `query = "... where dt = '${dt}'"` 这种写在引号里的引用也会被替换（HOCON 自己不会替换引号里的 `${}`）。值原样插入，不做转义
- **内置变量**：`system.biz.date`（计划时间前一天，yyyyMMdd）、`system.biz.curdate`（计划时间，yyyyMMdd）、`system.datetime`（计划时间，yyyyMMddHHmmss）、`system.window.start` / `system.window.end`（这次运行的同步窗口，yyyy-MM-dd HH:mm:ss，见 §7.5；预览时是下一次运行会读的窗口）、`system.task.instance.id`、`system.task.definition.name`、`system.project.name`
- **时间表达式**：`$[格式±N]` 中 N 是天数，可以写 `7*1`、`1/24`（1 小时）、`1/24/60`（1 分钟）；格式用 Java 日期格式。函数：`add_months(fmt,N)`、`this_day(fmt)`、`last_day(fmt)`（前一天）、`month_first_day/month_last_day(fmt,N)`（N 个月后的月初/月末）、`week_first_day/week_last_day(fmt,N)`（N 周后的周一/周日）、`year_week(fmt[,D])`（周所在的年和周数，D 为一周的第一天，1=周一，默认 1；格式含 `-` 时输出 `2026-43`，否则 `202643`）
- **参数名**只能是字母、数字、`_`、`.`，以字母或 `_` 开头；`system.` 前缀保留。参数值里可以用内置变量和 `$[...]`，**不能引用其他用户参数**
- 不认识的 `${name}` 原样保留并在运行时间线里记一条 WARN（多半是拼写错误），`${?x}` 永远不动。编辑器里的"预览渲染结果"会列出这些引用
- **参数编辑器**（项目参数、任务参数、启动参数共用 `components/ParamsEditor.vue`）：值按类型填写——固定值；日期时间（以计划时间为基准往前/往后 N 天/小时/月，或所在月第一天/最后一天、所在周周一/周日，再选格式，生成 `$[...]`）；内置变量（中文名下拉）；自定义表达式（手写）。每行显示 `${名称}` 引用写法（可复制）和按当前时间算出的示例值；名称格式、`system.` 前缀、重名当场标红并阻止保存。存储仍是名称 + 值字符串，编辑器能识别的值打开时还原成对应类型
- **已知冲突**：配置里任何 `$[...]` 都会被当作时间表达式。如果某个 connector 的选项本身要写 `$[`（比如 JSONPath 的方括号写法），保存时会报错，到时再加转义
- 保存版本时会用当前时间渲染一遍，再检查 HOCON 能否解析、数据源引用是否有效
- `job_instance.variables_json`：运行开始前只保存启动参数，开始后改为保存所有变量的最终值。手动运行可以指定计划时间，默认是当前时间

## 9. 运行、重跑与补数

| 操作 | 计划时间 | 版本 |
|---|---|---|
| 定时调度 | XXL-JOB 的触发时间 | 当前最新版本 |
| 手动运行 | 由用户指定，默认是当前时间 | 当前最新版本 |
| 重跑 | 沿用原实例的计划时间（和同步窗口，§7.5） | **默认用原版本**，可勾选"使用最新版本" |
| 补数 | 日期范围内的每一天 | 默认用最新版本 |

- 补数：选择日期范围，每个计划时间生成一个实例，通过 XXL-JOB 的 trigger OpenAPI 触发，并在参数里带上计划时间
- 上一次还没跑完时如何处理，交给 XXL-JOB 的阻塞策略（单机串行或丢弃后续调度）

实现细节（2026-10-24 实现并实测）：

- **重跑**：只能重跑已结束的实例。沿用原实例的计划时间和启动参数（`job_instance.startup_params_json`），变量按计划时间重新计算；默认用原版本，可选当前版本。新实例的 `trigger_type = RERUN`，`rerun_of_instance_id` 指向原实例。不做失败重试
- **补数的计划时间**：选的是计划时间的日期范围（两端都包含）。任务有调度时，按调度的 cron 生成范围内每个触发时间（和 DolphinScheduler 的补数一致）；没有调度时每天 00:00:00 一次。最多 1000 次。cron 在创建补数时快照到 `backfill_batch.cron`。只补已经到点的时间：结束日期最晚是今天，今天还没到的触发时间不补（批次按创建时刻截断，之后按序号推进时用同一个截断点）。同一个任务同时只能有一个未结束（进行中或暂停）的补数
- **补数的版本**：创建补数时的当前版本，整批都用它
- **补数逐个执行，不支持并发**：XXL-JOB 执行器对同一个任务只有一个线程，并发触发会排队；如果阻塞策略是"丢弃本次"或"停止上次"，还会被丢弃或互相杀掉。所以由 console 控制节奏：后台驱动每 5 秒检查一次，**只有该任务没有任何 PENDING 或 RUNNING 的实例时**（不论是谁触发的），才触发下一个计划时间。`parallelism` 固定为 1
- **失败不中断补数**，结束后可以单独重跑失败的那天。失败重试次数沿用调度配置（定时运行和补数生效，手动运行和重跑不重试）
- **暂停与继续**：XXL-JOB 接不了任务（比如 admin 不可用）时，这次运行记为 FAILED，补数改为 PAUSED 并记录原因；点"继续"后从这个计划时间重试。游标 `backfill_batch.next_index` 先用条件更新占位再触发，触发失败时退回
- **取消**：补数改为 CANCELED，正在运行的那次一起停止
- 补数进行中，定时调度仍会照常触发；它和补数的运行在 XXL-JOB 里按阻塞策略排队

## 10. 监控与数据校验

### 10.1 状态与指标

- 离线：由 XXL-JOB 处理器轮询，直到任务结束（第 5.2 节）
- 实时（P2）：console 定时任务每 10 秒同步一次状态，每 60 秒保存一次指标快照
- 轮询任务预留数据库锁，便于以后扩成多实例
- 日志：任务运行中通过 `/logs/{jobId}` 实时查看；结束后把最后 N MB 归档

### 10.2 运行实例详情页

任务详情和运行实例详情使用统一的页面样式，顶部分别标记“任务详情”和“运行实例详情”；实例页顶部同时展示完整运行 ID。

| 区块 | 内容 |
|---|---|
| 概览 | 状态、运行 ID（每次运行唯一的 instance.id）、计划时间、实际开始和结束时间、耗时、版本、最终变量值、读写行数、QPS、字节数、校验结果；运行实例列表也展示运行 ID |
| 事件时间线 | 提交 → 运行中 → 完成或失败（附错误信息），重试也记录在这里 |
| 指标 | 读写行数和字节数、引擎平均速率、运行中按轮询采样的吞吐量曲线、表级指标（§10.4）；P2 加上 CDC 延迟 |
| 日志 | 实时查看，加上归档日志 |

### 10.3 行数校验（P1）

- 离线实例跑完后自动执行：源端用和这次同步相同的 where 条件执行 `count(*)`，目标端用对应的条件统计（ES 用 `_count`）
- 结果为"通过"或"差值 N"，显示在实例上
- 局限：目标端只有在"清空后写入"或者能按增量字段过滤的时候才准确，其他情况下只能作为参考
- 逐行对比放到后续阶段

实现细节（2026-10-24 实现并实测）：

- 校验配置跟着版本走（`job_version.validation_json`，V4），在脚本编辑器下方配置，保存版本时检查配置是否可用
- **源端**："自动"从唯一的 Jdbc source 推导：有 `query` 时执行 `select count(*) from (query) t_count`，否则统计 `table_path`，两种情况都再加上 `where_condition`；也可以写自定义计数 SQL
- **目标端**：脚本模式下推导不出这次写入对应的过滤条件，所以由用户写计数 SQL，或者填 ES 索引和可选的 query（`POST /<index>/_count`）
- 计数 SQL、ES 索引和 query 都可以使用变量，和这次运行的取值相同
- 计数由 console 直接连数据源执行（只读连接，查询超时默认 10 分钟，`console.validation.timeout`），不依赖引擎上报的指标
- 结果：一致 PASSED、不一致 MISMATCH（显示差值）、计数失败 ERROR，没配置时为 SKIPPED。默认只做报告，不影响运行状态；勾选"不一致时把运行标记为失败"后，MISMATCH 会让运行失败（不会触发重试）。ERROR 永远不让运行失败
- 编辑器里的"测试校验"按当前时间立即执行一次计数，用来调试 SQL
- 校验用到的数据源也记录在 `job_version_datasource` 里，被引用时不能删除

### 10.4 任务详情、编辑页与引擎指标（2026-10-24 实现）

参考 Tapdata 的做法，把"看"和"改"分开：

- **任务详情** `/jobs/:id`：只看不改。页签为概览、运行记录（`/runs`）、补数（`/backfills`）、版本（`/versions`）。顶部是「编辑」「补数」「立即运行」和「更多 → 复制任务 / 删除任务」；没有权限时按钮置灰，悬停说明原因
- **概览**（`GET /api/jobs/{id}/overview`）：
  - 卡片：最近运行、调度（下次运行时间，可直接启用或暂停）、近 7 天成功率（成功 ÷（成功 + 失败），已取消不计入）、平均耗时（只算成功的）、写入行数
  - 正在运行时显示它的实时指标和吞吐量曲线，每 5 秒刷新
  - 同步链路（2026-10-26 重新设计，整行宽，放在统计卡片下面）：三段式「来源 → 处理 → 目标」。来源写数据源、库或接口（如 `GET /orders`）和表数；处理汇总向导里对数据做的事（过滤、裁剪字段、改名、替换、脱敏、类型转换、加密、提取和新增字段，按表累计，没有就写"原样同步"）；目标写数据源、库和"不存在时自动创建 / 报错"。下面一行是同步方式（含增量窗口和字段）、写入方式、已有数据、并行度、行数校验，都是按来源能力生效后的值（如 HTTP 无主键只能追加）。最后是表映射：源表 → 目标表，每张表注明过滤、增量字段和字段处理，超过 5 张默认折叠，可筛选。脚本任务从 HOCON 读出来源、目标和 transform 插件名，没有表映射和同步方式。字段级明细不在这里展示（勾选全部字段的表要连数据源才知道字段），看细节进向导
  - 最近 30 次结束的运行：耗时柱状图（颜色表示结果）加写入行数折线，点柱子进入那次运行
  - 最近一次有指标的运行的表级指标；最近结束的 10 次运行
- **编辑页** `/jobs/:id/edit`：同步配置（向导或脚本）、调度（`/edit/schedule`）、基本信息（`/edit/basic`，名称、描述、所属项目）三部分各自保存，只有同步配置生成新版本。向导每一步都能保存，保存时先检查前面各步，再做预检查，有错误就停在出错的步骤或预检查页。有未保存修改时页签上有标记，离开页面会确认。没有权限的人打开编辑地址会被带回详情页
- 任务移到另一个项目需要对目标项目有修改权限，之后运行时引用的是新项目的参数；已有运行记录的 `project_id` 不变

**引擎指标**：BatchJobRunner 每次轮询（默认 2 秒，`console.run.poll-interval`）拿到 `/job-info` 的 metrics 后：

- 覆盖 `job_instance_attempt.metrics_json`（最新快照），并更新 `job_instance` 的读写行数和字节数（只更新这几列，不会覆盖并发的停止操作），所以列表和概览在运行中就能看到进度
- 往 `job_metric_sample`（V7）写一行累计值；吞吐量曲线由相邻两点的差值算出（行/秒），不存速率
- `EngineMetrics` 解析出总量（`SourceReceivedCount`、`SinkWriteCount`、字节数、引擎给出的平均 QPS）和表级指标（`TableSourceReceived*`、`TableSinkWrite*`，键为 `Source[0].库.表`，值是一段 JSON 字符串）
- 运行实例详情页新增"运行指标"区块（`GET /api/instances/{id}/metrics?attemptNo=`），按尝试分别显示

`job_metric_sample` 目前不清理，每次运行约"运行秒数 ÷ 2"行；等日志保留策略（P3）一起做清理。

### 10.5 概览页（2026-10-24 实现）

## 12. 分阶段规划

### P1 离线

- 账号、角色、项目、项目参数
- 数据源中心：MySQL、PG、ES
- 场景化向导（高级参数中文化）、脚本模式（可插入 transform 模板）
- 离线同步：MySQL/PG → MySQL/PG/ES，全量和增量
- 选表支持正则检索；表映射和字段映射（按规则或逐个改名、屏蔽字段）；字段处理（替换、脱敏、类型转换、加密、新增和提取字段）
- 任务复制；参数编辑器（按类型选值）；调度按频率设置
- 版本管理；变量；XXL-JOB 调度；手动运行、重跑、补数
- 运行实例详情页；行数校验；集群健康检查
- Docker 交付

### P2 实时

- MySQL-CDC、Postgres-CDC → MySQL/PG/ES
- 前置条件检查：MySQL 要开启 binlog 且格式为 ROW；PG 要设置 `wal_level=logical` 并开放复制权限
- 实时任务操作约定：
  - 停止：默认 savepoint 停止，可以选强制停止
  - 启动：有 savepoint 时默认从它恢复（`restoreMode=SAVEPOINT`），也可以从最近的 checkpoint 恢复，或全新启动
  - 失败后自动重启：按任务开启，从最近的 checkpoint 恢复，最多 N 次，**默认关闭**
  - 编辑正在运行的任务后，提示"新版本待重启生效"
- 正则规则动态选表（运行时匹配，新表自动纳入）
- RPS 和延迟的趋势图
- 复用向导的表 / 字段映射和字段处理；行级的 `FilterRowKind`、`RowKindExtractor` 等到这时再做
- 导航（2026-10-25 初步商定，P2 开始时再确认）：菜单分成两个入口——现在的「任务」改名「离线同步」，新增「实时同步」；「运行记录」（现「运行实例」）只放离线的每次运行，实时任务的启停历史放在它自己的详情页；项目、数据源、集群健康、加密密钥两边共用；概览页加实时任务的状态（运行中 / 异常数、最大延迟）

#### P2 已确认的决定（2026-10-26）

- **范围**：MySQL-CDC、Postgres-CDC → MySQL / PG / ES。HTTP、ES 来源不做实时；其他 CDC 留到 P3
- **数据模型**：实时任务是 `job_type = STREAMING` 的 `job_definition`，版本、项目、所有权、复制、版本对比和回滚都复用。一次"启动 → 停止或失败"是一条 `job_instance`，事件、日志归档、指标采样复用；它不出现在「运行记录」里，只在实时任务详情页的"启停历史"里
- **驱动**：不经过 XXL-JOB，没有调度和补数。console 直接调 Zeta 启停，每 10 秒同步状态、每 60 秒存指标快照；console 重启后按记录的 engine jobId 重新接管。变量只有项目 / 任务 / 启动参数，时间类内置变量取启动时刻
- **导航**：按 2026-10-25 的方案，改名作为 P2 的第一个提交
- **从哪里开始同步**（向导）：全量 + 增量（`initial`，默认）/ 只同步之后的变更（`latest`）/ 从某个时间点开始（`timestamp`，仅 MySQL）。其他启动方式只在脚本模式
- **选表**：先只做明确清单，逐表配置映射和字段处理。正则动态选表等实测引擎行为后再单独讨论（`table-pattern` 看起来只在启动时匹配）
- **主键和删除**：无主键的表不能选；写入固定按主键 upsert，没有"清空后写入"；删除默认同步，可开"不同步删除"（`FilterRowKind` 过滤 DELETE）
- **前置条件**：预检查、每次启动和实时同步列表页的"检查同步条件"（选一个源数据源查看；2026-10-27 从数据源页挪过来，条件是给建实时任务的人看的）检查 MySQL `log_bin=ON`、`binlog_format=ROW`、`binlog_row_image=FULL`、`REPLICATION SLAVE / CLIENT` 和 `SELECT` 权限；PG `wal_level=logical`、`REPLICATION` 权限、所选表 `REPLICA IDENTITY FULL`。不满足时给修复 SQL，console 不改用户的库
- **server-id / slot.name**：console 自动分配。MySQL 每个任务一段不重复的 server-id（长度 = 并行度），高级参数可手改；PG 的 slot 名为 `seatunnel_<任务 id 前缀>`。删除 PG 实时任务时先停作业，再用数据源账号 `pg_drop_replication_slot`（对话框默认勾选"同时删除复制槽"，失败时给出 SQL）
- **启停**：停止默认带 savepoint，可强制停止；作业还没提交到引擎（启动或自动重启进行中）时不能停止，提示稍后再试，免得 console 记为已停止而随后提交的作业没人管；等待自动重启时停止会取消这次重启（和监控线程抢同一条条件更新，只有一方成功）；启动默认从 savepoint 恢复，可选最近的 checkpoint 或全新启动；用来源设置有变化的新版本启动时默认改为全新启动，并醒目提示会重新全量。失败自动重启默认关闭，打开后最多 3 次、间隔 30 秒、从最近的 checkpoint 恢复，连续运行 10 分钟后计数清零
- **一致性**：`exactly_once = false`（至少一次 + 按主键 upsert），`checkpoint.interval` 默认 10 秒，高级参数可改
- **表结构变更**：第③步"同步表结构变更"开关，新建时默认打开（按下面的实测结论，2026-10-26 修订）：
  - 目标 MySQL / PG：加列、改类型、改名固定同步（`schema-changes.include = ["add.column", "modify.column", "change.column"]`，再加上可选的 `drop.column`）；只保留"同步删列"一个选项，默认不勾。不勾时目标列保留、之后写入为空，目标端 NOT NULL 的列预检查警告（SeaTunnel 自动建表不带默认值）。改名和改类型不能排除：排除后会静默写坏数据
  - 目标 ES：只能同步加列。改名、改类型也放进 `include`，让任务明确失败而不是静默写坏；删列排除（ES 没有 NOT NULL，排除是安全的）
  - 来源 PG：只有加列，改名 / 改类型 / 删列会让任务以 SE-07 停下
  - 和字段处理二选一：开关打开时不能用 Sql 类字段处理（替换、脱敏、类型转换、新增和提取字段），反之亦然。字段加密也算在内：`FieldEncrypt` 本身不怕 DDL，但加密字段要先在 Sql 里转成文本（§7.11），表里任何一列改名或删列都会让任务失败（2026-10-27 更正）。改字段名、改表名、屏蔽字段可以一起用；改过名和被屏蔽的列在第③步列出并提示"以后不能在源端改名、删除或改类型"
  - 实时任务的屏蔽字段用 `Filter { exclude_fields }` 生成；"不同步删除"的 `FilterRowKind` 必须放在 transform 链的最后
  - 开关旁说明：源端改列名请用 `CHANGE COLUMN`，MySQL 8 的 `RENAME COLUMN` 不会被同步
- **表结构变更的反馈**：console 运行期间每 5 分钟对比源表、目标表与启动时记录的结构，变化写进事件时间线（例如"orders 新增列 remark → 目标端已同步 / 未同步及原因"），详情页表映射里标出有变化的表和逐列差异；因 DDL 失败时写明哪张表哪条 DDL 和处理办法。之后打开向导按源表当前结构显示字段并标出新增 / 删除 / 改名，保存后才生成新版本
- **延迟**：优先用引擎的 `CDCRecordEmitDelay`；`/job-info` 拿不到时只显示"最近一次读到数据的时间"
- **详情页**：按钮 启动 / 停止、编辑、更多（复制 / 删除）；页签 概览（状态、运行时长、当前版本和"新版本待重启生效"、延迟、RPS 趋势、表级指标、同步链路、表结构变更）、启停历史（点进现有实例详情页）、版本。启动对话框选恢复方式并显示启动参数
- **并行度**：1 / 2 / 4 / 8，默认 1，作用于全量快照阶段
- **不做**：行数校验。脚本模式支持，检查 `job.mode = "STREAMING"`，凭据注入、打码和归属检查照旧
- **checkpoint 保留**：console 给所有实时任务的 env 加 `checkpoint.retain-after-job-cancelled = true`，强制停止和失败后都能从 checkpoint 恢复
- **DDL 导致的失败**：启动对话框默认"全新启动"并说明原因，从 checkpoint 恢复置灰（会重放同一条 DDL 再次失败）
- **自动恢复中的状态**：`/job-info` 在 pipeline 自动恢复期间仍是 RUNNING；console 读 `diagnostics.pipelines[].restoreCount`，大于 0 时显示"运行中（异常，正在自动恢复第 n 次）"，记事件并计入异常数。不显示上限：引擎的恢复次数上限是集群配置，REST 接口读不到
- **代码组织**：按模块拆分（CDC 来源是新的 `WizardSource`，流任务的启停、监控、结构对比各自成类），不往已有的批处理类里堆分支

#### P2 实现说明（2026-10-27）

- **代码位置**：CDC 来源是 `job/wizard/source/CdcSource`，实时任务专用的 transform 和预检查在 `StreamTransforms`、`StreamPrecheck`；启停、监控和恢复都在 `stream/` 包：`StreamService`（启动、停止、设置、删除）、`StreamMonitor`（定时跟踪引擎作业）、`StreamSubmitter`（渲染并提交）、`StreamRuns`（运行记录）、`StreamIdentityService`（server-id 段和复制槽名）、`CdcReadiness`（实时同步条件）；纯规则 `RestorePlan`、`AutoRestartPolicy`、`CheckpointHealth`、`StreamFailure` 单独测试。数据源的检查在 console-datasource 的 `CdcSupport`（`MySqlCdcSupport`、`PostgresCdcSupport`）
- **恢复位置跟着 checkpoint 走**：运行中的作业一旦完成过 checkpoint，`job_stream.restore_*` 就指向它；还没完成过的（例如全量阶段就失败）保持启动时的位置（savepoint，或者没有）；全新启动的作业提交到引擎后清掉上次留下的位置，免得首个 checkpoint 之前失败的自动重启回到旧位置（提交前失败则保留，2026-10-27 补）。提交前先记下 console 选定的引擎作业 id，console 在提交途中退出，重启后仍按这个 id 找回作业。所以失败、强制停止后的恢复和自动重启都从"最近一次真正完成的 checkpoint"开始，没有就全新启动。正常停止记 savepoint
- **env 里的选项按完整名字传**：console 渲染配置时 `checkpoint.interval` 这类带点的 env 选项保持为一个键。标准 HOCON 会把它解析成嵌套对象，而 Zeta 按完整名字查 env（`checkpoint.retain-after-job-cancelled`），嵌套后不生效（2026-10-27 实测发现并修复）。connector 选项按路径读取，嵌套没有影响
- **全新启动前重新预检查**：向导任务全新启动时按源表、目标表的当前结构再跑一遍预检查，有错误就拒绝启动并说明（比如源表改了列名，映射里的字段已经不存在），而不是等引擎在写入时失败。从保存的位置恢复时不检查
- **性能取舍**（Q30、Q31）：状态每 10 秒查一次（只查运行中的任务）；计数、吞吐量采样和 checkpoint 状态每 60 秒一次（`console.stream.sample-interval`），所以"最近读到数据的时间"和 checkpoint 时间的精度是一分钟；复制槽占用的 WAL 只在打开已停止任务的详情时查；启动时的条件检查每次启动做一次
- **表结构变更的反馈**（Q16）：`SchemaDriftWatcher` 每 5 分钟（`console.stream.schema-interval`）只读运行中的向导实时任务的源表和目标表，和上次看到的结构（`stream_table_schema`，启动时先记一次）对比；源表有变化时在这次运行的时间线里记一条 SCHEMA_CHANGE 事件，逐条写明加列、改名、改类型、删列，以及目标端是否已经跟上、没跟上的原因（没开同步、PG / ES 只同步加列、MySQL 8 的 RENAME COLUMN 不同步、没勾删列等）；目标端没跟上的记为 WARN，详情页概览的「表结构变更」列出最近 10 条。改名的判断：同一位置、同类型的列消失又出现。DDL 一般在这张表下一次有数据变更时才传到目标端，所以刚改完时可能显示"还没有变化"。详情页同步链路的表映射按 `stream_table_schema.start_columns_json`（每次启动时记下）和最近一次看到的结构对比，把启动以来结构变了的表排在前面，逐列写明目标端是否跟上（需要处理的标黄）；停止后保留到下次启动。时间线事件和表映射用同一套判断（`SchemaFollow`）
- **向导里标出源表的变化**（Q17）：数据库来源的向导每次保存时把字段映射里看到的源表字段（名字和类型）记进表单（`TableSpec.seenColumns`，只给向导用，不影响生成的配置）；再次编辑时和源表现在的结构对比（规则同 `SchemaDiff`，前端 `utils/columnChanges.ts`），在表列表标"结构有变化"，字段行标"新增""改名，原 x""（原类型）"，已删除的列列在表格下面。删除的列还被设置用到时（同步字段、目标字段名、处理、增量字段）点"清理设置"去掉，否则预检查报"字段不存在"不能保存；改名的列默认按新字段处理，点"沿用原设置"把同步与否、处理、增量字段和原来的目标字段名搬到新名字上，目标表不用跟着改。实时任务里源表新加的列运行时已经在同步（屏蔽字段按名字排除），所以同步字段是列表时自动加进去，免得保存后反被屏蔽。源表有变化本身就算"有未保存的修改"：保存会更新配置（例如实时任务的屏蔽字段列表跟着改名），保存后标记消失。之前保存、没有记录的版本不标
- **集群诊断的实时任务检查**（Q31）：`health/StreamProbe` 提交一个很小的 FakeSource 流作业（每 2 秒一次 checkpoint），等到完成一次 checkpoint，再带 savepoint 停止、从 savepoint 恢复、最后停止，哪一步不成就说明是哪一步；和批量的诊断作业同时跑。快速检查里 worker 多于 1 个时固定提醒 checkpoint 要放共享存储（REST 接口读不到这项配置）
- 运行记录列表和"运行中的批量运行在 console 重启后记为失败"都不包括实时任务的运行（`trigger_type = START`）；离线任务的立即运行、重跑、补数和调度接口拒绝实时任务

#### P2 实测结论（2026-10-26，SeaTunnel 3.0.1-SNAPSHOT 单节点，直接向 Zeta 提交）

| 源端 DDL | MySQL → MySQL | MySQL → PG | MySQL → ES | PG → MySQL |
|---|---|---|---|---|
| 加列 | 同步 | 同步 | 同步 | 同步 |
| 改类型 | 同步 | 同步 | 任务失败 | 任务失败（SE-07） |
| 改名 `CHANGE COLUMN` / PG `RENAME COLUMN` | 同步 | 同步 | 任务失败 | 任务失败（SE-07） |
| 改名 MySQL `RENAME COLUMN` | **被忽略**：之后这一列写成 NULL，再对它做 DDL 任务失败 | - | - | - |
| 删列 | 同步 | 同步 | 任务失败 | 任务失败（SE-07） |

- 从 `include` 排除某类 DDL：排除删列时目标列保留、写 NULL（目标 NOT NULL 时失败）；**排除改名或改类型会静默写坏数据**（改名后的列在目标端为 NULL；int→bigint 后超范围的值溢出成负数写入），任务仍是 RUNNING
- transform：TableRename、FieldEncrypt 对各种 DDL 都正常（加密跟着改名后的列走）；FieldRename 对改过名的那一列做改名或删除时任务失败；`Filter { exclude_fields }` 新列照常同步，对被屏蔽的列做 DDL 任务失败；Sql 遇到加列时 pipeline 失败一次再自动恢复、新列在目标端为 NULL，表里任何一列改名或删除任务失败；`FilterRowKind` 放在其他 transform 前面时遇到改名会失败，放在最后正常
- 启停：savepoint 停止后用 `restoreMode=SAVEPOINT&restoreSourceJobId=<原 id>` 恢复，沿用原 jobId、不重新全量；`restoreMode=CHECKPOINT` 恢复得到新 jobId，只有设置了 `checkpoint.retain-after-job-cancelled` 的作业在强制停止后还有 checkpoint；失败的作业保留 checkpoint，但 DDL 导致的失败恢复后重放同一条 DDL 再次失败；新版本加了表再从 savepoint 恢复时，目标表不会自动创建，作业反复失败
- 指标：`/job-info` 没有 CDC 延迟指标（`CDCRecordEmitDelay` 不在其中），延迟只能显示"最近一次读到数据的时间"
- PG：非超级用户不能建 `FOR ALL TABLES` 的 publication，要用 `debezium { publication.autocreate.mode = "filtered", publication.name = ... }`；任务停止后复制槽和 publication 都留在库里，删除任务时两者都要清理
- 库名带 `-`（如 `source-cdc`）对 MySQL-CDC、Postgres-CDC 和 Jdbc sink 都没有问题
